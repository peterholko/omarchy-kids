# Security

Omarchy takes security extremely seriously. This is meant to be an operating system that you can use to do _Real Work_ in the _Real World_. Where losing a laptop can't lead to a security emergency. So here's what we do:

1. *Full-disk encryption is mandatory*: This is the most important step to securing the physical protection of your data. If your computer is lost or stolen, the data is fully encrypted using standard LUKS (Linux Unified Key Setup).
2. *Firewall is enabled by default*: All incoming traffic is blocked by default except for port 53317 for [LocalSend](https://localsend.org/). Even ssh is off until you turn it on via _Setup > Security > SSHD_, which opens port 22 (rate limited against brute force) as part of the setup. We even lock down Docker access using the [ufw-docker](https://github.com/chaifeng/ufw-docker) setup to prevent that your containers are accidentally exposed to the world.
3. *Arch always have the latest updates*: Arch, the underlying distro that Omarchy is built on, is a rolling distribution. This means that any security vulnerability that's discovered and patched in any package is quickly available for install using `omarchy-update`. You're always running the latest, most secure versions of everything that way.
4. *Omarchy maintains its own packages and mirror*: Omarchy only relies on packages from Arch's own core/extra/multilib repositories and its own Omarchy Package Repository by default. You can install software directly from AUR, but the base install doesn't — only a few optional installs, like the third-party browsers, pull from the AUR.
5. *Cloudflare protects us from DDoS*: All the Omarchy distribution infrastructure — the ISOs, the Omarchy packages, the Arch mirror — is protected behind Cloudflare's formidable DDoS shield and hosted on their CDN. This provides superb availability.

## Changing your passwords

You have two passwords on an encrypted install: the one that unlocks the drive at boot, and the one you log in and `sudo` with. Both can be changed under _Update > Password_ in the Omarchy menu — _Drive Encryption_ for the first, _User_ for the second. Changing the drive password asks for the current one first, so have it handy. A child install has a third, the parent password, under _Update > Password > Parent_; see below.

## Child installs

Pick _Child_ at the installer's first question and the machine is set up for a kid with two passwords. The **kid password** is the account password: it logs in, unlocks the screen, and unlocks the disk at boot. The **parent password** is root's password, and it is what every privileged path asks for: `sudo`, system prompts, _Update > Omarchy_, every _Install_ and _Remove_ entry, the Windows VM and the Docker TUI, _Setup > Reset Computer_, passwordless sudo, the DNS toggle, and the timezone menu. The kid's account is not an administrator: it is kept out of the `wheel` group on purpose, so nothing that trusts that group reaches it, and _Setup > Security > Passwordless Sudo_ and _Sudoless Docker_, which would hand the account root without a password, are not offered on a child install. Everything that never needed root is the kid's to use: Bluetooth, themes, screenshots, printing, the apps, and the Wi-Fi networks the machine already knows.

Both passwords unlock the disk, and both open the lock screen and the login screen, so a parent can get into the kid's session, locked or logged out, without asking for the kid's password; the login is the kid's account either way. When screen time is on, each successful parent-password unlock or login adds five minutes to the kid's bank; the kid password and fingerprint add nothing. One limit: ten wrong tries lock the kid's account for two minutes, and during those two minutes the parent password waits too. If the kid forgets theirs, boot with the parent password and reset it from a terminal with `sudo passwd <kid>`, which asks for the parent password first. The kid can change their own login password under _Update > Password > User_ at any time; that does not change the disk password, same as on any install.

Joining a new Wi-Fi network, or changing one, asks for the parent password as well: that is a system setting, and NetworkManager only waves it through for administrators. When the kid needs to join a network alone, at school say, run `sudo omarchy-kids wifi kid`; `sudo omarchy-kids wifi parent` puts the prompt back, and `sudo omarchy-kids wifi` shows the setting. The choice lives as `wifi=` in `/etc/omarchy/parent.conf`, which a parent can also edit by hand and apply with `sudo omarchy-kids apply --user <kid>`. Either way, connecting to a network the machine knows, scanning, and the Wi-Fi switch never ask, and the DNS toggle keeps asking.

A child install also comes set up for a kid rather than for work: the launcher is school and creativity. It shows the browser, LibreOffice, Files, the document, image, and media viewers, Omawrite, Omacalc, Pinta, Xournal++, Aether, Obsidian, Kdenlive, Cliamp, Google Maps, Khan Academy, and Wikipedia. The chat, mail, social, and AI shortcuts (Discord, X, WhatsApp, Google Messages, HEY, Basecamp, ChatGPT, Grok), Zoom, Docker, Disk Usage, and the terminal entry are not there, and neither are the agent command-line tools; the terminal itself keeps `Super + Return` for the parent. YouTube has no shortcut either: a kid reaches it through a supervised Google account in the browser, with YouTube's "older kids" setting, rather than an unrestricted shortcut. The keyboard shortcuts follow the same set, with `Super + Shift + M` opening Cliamp, and Khan Academy (`Super + Shift + K`) and Wikipedia (`Super + Shift + Alt + K`) on the freed keys. The menu's Community link to Discord, the package and AUR installers, and the AI and developer rows are off the kid's menu; a parent reaches those from a terminal. The theme switcher offers a child-friendly set, starting on Bubblegum, whose colours the boot and login screens take as well and whose accent the Omarchy wordmark wears there, in the terminal, and on the first-boot screens, and the kid can still add themes of their own; the web filter and the app list, below, are the parent's tools for the rest. There is no screensaver on a child install: two and a half minutes idle goes straight to the lock screen, dark and still, and the display switches off a few seconds later; the screensaver rows leave the kid's menu, and a parent can still start one from a terminal with `omarchy-launch-screensaver force`.

Change the parent password under _Update > Password > Parent_, or with `sudo omarchy-kids password` in a terminal. That changes root's password, not the disk slot that goes with it: to rotate that as well, run _Update > Password > Drive Encryption_ and type the old parent password when it asks for the current one.

Two things to know. `sudo` remembers a password for a few minutes in the terminal it was typed in, and system prompts remember an authorization for a similar spell, so close the terminal when you are done administering. And the split protects the running system, not the hardware: someone with a live USB and the kid's disk password can reset root's password from outside, so on a kid's laptop set a BIOS password and lock the boot order. A child install does not filter the web on its own; that is a separate layer.

Fingerprint unlock still works for the kid at the lock screen, but `sudo` and system prompts keep asking for the parent password, and FIDO2 setup is not offered because it only ever covered those two. Child installs also close the text consoles behind Ctrl+Alt+F2 through F6, so the lock screen is the only way back into a locked session; `sudo omarchy-kids tty on` reopens them.

### Web filter

A child install filters the web from its first boot: every lookup is answered by [Cloudflare for Families](https://developers.cloudflare.com/1.1.1.1/setup/#1111-for-families), which drops malware and adult sites without a list to keep, and the deny list starts empty. `sudo omarchy-kids dns` is the parent's command for it. `sudo omarchy-kids dns deny tiktok.com` refuses a site of your own choosing under that default, denylist mode. `sudo omarchy-kids dns allowlist` refuses everything except the domains you allow, `sudo omarchy-kids dns allow khanacademy.org`, plus a short list the machine needs for updates and time. A site is many domains: YouTube needs `youtube.com`, `googlevideo.com`, `ytimg.com`, `ggpht.com`, and `google.com`, so `sudo omarchy-kids dns log` shows the names a page just asked for and was refused, most often first, ready to allow. A denied name wins over an allowed one, so `allow google.com` with `deny mail.google.com` does what it says. `sudo omarchy-kids dns upstream auto` answers allowed names through the network's own servers instead of Cloudflare for Families, which a sign-in page that blocks outside DNS can need until the parent is signed in; `upstream family` puts Cloudflare back. `sudo omarchy-kids dns off` removes all of it and keeps your lists.

The lists are `/etc/omarchy/parent/dns.allow` and `dns.deny`, one domain per line; edit them and run `sudo omarchy-kids dns apply`. An entry with a path is a page, not a domain, and the browser refuses it rather than the resolver, which cannot see paths: `sudo omarchy-kids dns deny youtube.com/shorts` keeps YouTube open but closes the Shorts feed, in Chromium and Firefox alike, under either mode. A page the kid reaches another way, the same short opened as an ordinary video for instance, is not caught; the domain lists are the firm ground, the page list the trim. The filter runs as root: the kid's session cannot reach another resolver on the usual ports, the browsers are told not to use DNS over HTTPS, and a stopped filter means no web rather than an open one. It does not stop a VPN or proxy app (installs ask for the parent password), a browser extension that tunnels, or an address typed as numbers; the app allowlist is the other half. After installing another browser, run `sudo omarchy-kids dns apply` so its policy is written too.

The filter also keeps a log of every site the laptop asked for, in the system journal, where the kid can neither read nor clear it. `sudo omarchy-kids dns history` lists the last day's sites, most often first, with when each was last seen; `history 7` covers a week. It records sites, not pages, and only while the filter is on. Tell your kid the log is there: the point of a preteen's setup is safety, not surveillance, and a log they know about is a boundary rather than a trap.

### App allowlist

A child install starts with its app list on, in denylist mode: every app is there except a short list a parent opens when the time comes, `sudo omarchy-kids apps allow LocalSend` for instance. That starting list is the apps an eleven-year-old opens only with supervision (LocalSend, Moonlight, OBS Studio) and the terminal's own launcher entries, btop, Neovim, Disks, and the Avahi browsers; `sudo omarchy-kids apps list` shows every app with its verdict. `sudo omarchy-kids apps deny Steam` adds to the list; `sudo omarchy-kids apps allowlist` keeps only the ones you allow, and an app installed later stays hidden until you allow it. Switching to allowlist with nothing allowed yet starts from every app installed today, so nothing disappears by surprise. Name apps as the launcher shows them, or by the id `sudo omarchy-kids apps list` prints beside each one. A blocked app leaves the launcher and its program stops running for the kid, even from a terminal; package updates put the list back on their own. `sudo omarchy-kids apps off` gives everything back and keeps your lists, which are `/etc/omarchy/parent/apps.allow` and `apps.deny`, one id per line, applied with `sudo omarchy-kids apps apply` after a hand edit.

Two things follow from how it works. Some apps share one program, LibreOffice's Writer and Calc for instance, so denying only one of them hides it from the launcher but leaves the program running for the other; `list` says so. And the terminal is never blocked, because the floating terminal is how you run `omarchy-kids` from the menu; the web filter and the parent password around installs are what bound what a terminal can do. Web apps are the browser in another window: govern them with the web filter, or block the browser itself.

### Browsing history

DNS filtering can tell you a site was visited, but not which page: `youtube.com`, not which video, because HTTPS hides the rest. To know exactly what was watched, `sudo omarchy-kids browsing on` keeps the kid's browsing history where she cannot erase it. From then on a root task collects it every minute from the browser's own history and from the titles of the windows on screen, and the browser is told by policy not to offer a private window or let history be cleared. `sudo omarchy-kids browsing videos` lists the YouTube videos watched, most recent first, with the title, how often each was opened, and how many minutes it was on screen; `sudo omarchy-kids browsing pages` lists every page. `sudo omarchy-kids browsing off` stops collecting and keeps what was kept, readable only by root.

This is the most watchful thing in kids mode, so use it deliberately. The browser shows it is managed while it is on, and the honest thing, and the more effective one for a preteen, is to tell your kid the history is kept rather than to watch in secret. It records sites and video titles, not keystrokes or content, and only for the account you turn it on for.

A child install can also take extra parent features from git, which are not part of the default image: `sudo omarchy-kids plugin add <git-url> --enable`.

### Screen time

_Math time_ is the child install's arithmetic app, in the launcher and the Omarchy menu. Opened on its own it offers a practice set: ten questions at any grade from 1 to 6, each with a second try before the answer is shown, a running count of how many in a row, and a results screen with the score and the best run; nothing is timed. Practice earns nothing and needs nothing turned on. A child install can also make the kid earn her screen time with it: turn that on with `sudo omarchy-kids time on`. From then on her day starts with a budget of minutes (an hour, ninety at the weekend), a pill in the bar shows what is left, it counts down while the screen is unlocked and she is at it, she is warned at fifteen, five, and one minute, and at zero the screen locks ten seconds later. The bank stops exactly at zero: neither the countdown nor the parent's take-away control can create hidden debt, and an older overdrawn day is repaired when the daemon loads it. She unlocks with her own password, and instead of her desktop she gets _Math time_ full screen, in its earning mode: a set of ten questions at the grade you set earns thirty minutes when every answer is right, each right answer worth its share; each right answer just says Correct, a miss shows the answer and moves on, and the screen time the set earned is shown at the end. Math time can stay open for the entire set, however long the questions take. On this post-unlock Math screen, Escape opens a parent-password prompt; the right password adds five minutes, closes Math time, and returns to the desktop. Closing the app without that still brings it straight back, and if Math time is missing or the shell is stopped, the screen locks again after one minute. Unlocking with the parent password also adds five minutes. Omacalc is closed and cannot be opened while _Math time_ is on screen, but remains available normally. While screen time is on, the app's start screen offers _Earn time_ beside _Practice_, and the bar's pill opens a panel with the day's use, a button for _Math time_, the sums she has done today, and, behind the parent password, quick controls for you: fifteen or sixty minutes more, fifteen fewer, a pause, and the settings window.

The grades run from 1 to 6, all practising arithmetic facts for quick recall. Addition uses pairs from 2 through 10, with totals up to 20; subtraction asks the matching facts, such as `15 − 8 = 7`. Grade 1 practises those addition and subtraction pairs. Grade 2 adds the times tables from 2 to 5, grade 3 includes multiplication and division tables through 10, and grade 4 reaches 12 × 12. Grades 5 and 6 practise only multiplication and division tables through 12 × 12. Division always has a whole-number answer. Facts she gets wrong come round again more often. Earning questions are at the grade you set with `sudo omarchy-kids time level grade5`; practice is at whatever grade she picks. The ratio is yours to set: `sudo omarchy-kids time earn 4 30` makes a set four questions for thirty minutes, seven and a half per right answer; `questions 12` changes the count and keeps the minutes, and `rate 5` is the old way round, minutes per right answer. `cap 90` bounds the minutes she can earn a day, and `budget 45 weekdays` (or `budget 90`, every day) sets the minutes each day starts with. The same settings, and the minutes per weekday, are in the settings window behind the pill.

`sudo omarchy-kids time grant 30` banks time outright, for a homework night or a reward; `pause` stops the countdown until `resume`, and `lock` locks her screen now. `status` says where she stands, `report` prints a day's budget, use, earnings, and every question with its outcome (`report 2026-09-01` for a past day), and `history` the last two weeks by day. `sudo omarchy-kids time off` stops all of it and keeps the days.

School hours are not screen time. `sudo omarchy-kids time school mon-fri 08:00-15:30` makes those hours free: nothing counts down and nothing locks, so the laptop is hers for schoolwork; give several windows as more pairs (`sat 09:00-11:00`), name days as `mon-fri`, `mon,wed,fri`, `weekdays`, `weekends`, or `daily`, and `school off` clears them. The gear in the School Mode panel opens a focused editor for the same schedule after asking for the parent password. School hours are also **school mode**: the desktop changes shape for the work. The menu and the launcher show only the school apps (the browser, LibreOffice, Files, the document and image viewers, Omawrite, Omacalc, Xournal++, Obsidian, Khan Academy, Wikipedia, and Math time; no games, no music, no video), the shortcuts to anything else are lifted for the duration, notifications go quiet, and whatever she had open is parked out of sight and comes back afterwards. The browser is the same one in both modes. The rest of the day is **free time**: the whole child launcher and notifications. A pill on the bar says which mode is on, a book for school and a sun for free time, and its panel says why. She can start school mode herself whenever she wants to work, but that choice still uses her screen-time allowance so it cannot become a way around the limit. Returning from school mode to free time always asks for the parent password; `auto` cannot bypass that when it would return to free time. A scheduled start enters school mode automatically unless the parent deliberately chose free time during that same school period. When you run `sudo omarchy-kids time mode school`, the parent-authorized school mode pauses her allowance until you choose `free` or `auto`, or until midnight; bedtime still locks the screen. `auto` means the schedule decides. `sudo omarchy-kids time school-apps` lists the school apps, and `school-apps add obsidian` and `school-apps remove omacalc` change them, by the id the launcher uses. The web filter is the same in both modes. `sudo omarchy-kids time bedtime 20:00-07:00` is the other kind of period: the screen locks between those times every night, `bedtime off` lifts it, and the settings window can add more, dinner for instance, each with its days and whether it locks or is school time.

A deliberate choice that resolves to Free Time always requires the parent password, even when Free Time is already active. Choosing School Mode does not require it; choosing `auto` requires it only when the schedule would resolve to Free Time.

The counting, the warnings, the locking, and the checking of answers all run as root, in a daemon the kid's account cannot stop or write to; the answers never reach her machine's side of it, an answer within a second and a half is not counted, and setting the clock back changes nothing, because the daemon counts on the boot clock. Time counts only while her session is active and the screen is unlocked; sleeping and the lock screen do not count. The screen stays on while _Math time_ is open, paper and pencil included. A kid who writes a program to solve her own arithmetic has, in fairness, earned the time. The daemon and the bar's pill are Jankees van Woezik's [omarchy-screen-time](https://github.com/jankeesvw/omarchy-screen-time), adapted for kids mode.

## Passing on a machine you've already used

If you're handing your machine over to someone else, you don't have to reinstall it. Run _Setup > Reset Computer_ in the Omarchy menu, type `reset` to confirm, and reboot. That wipes every user account and everything in `/home`, throws away all the packages and system changes you made since installation, and clears the machine's identity — network connections, host keys, and all. What comes back up is the setup wizard from the first boot, ready for its new owner to enter their own name, password, and encryption password.

It works by restoring the baseline snapshot the installer takes, so it's only available on machines installed from the Omarchy ISO. And on a drive without encryption, a reset is deletion rather than a secure erase, so if the data was sensitive, do a fresh install instead.

## Passwordless sudo

Sometimes you want `sudo` to stop asking, most often when an AI agent is doing a long stretch of system work for you. _Setup > Security > Passwordless Sudo_ turns that off for 15 minutes and then puts it back automatically. Run it again before the timer runs out to end it early, and pass your own number of minutes with `omarchy-sudo-passwordless 30` if 15 isn't enough.

Be clear-eyed about this one: while it's on, anything running as your user can do anything as root without being asked. That's the whole point, and it's also the whole risk.
